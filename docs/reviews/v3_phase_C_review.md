### C-R08 活跃尝试缺少互斥登记与真实进程身份门禁（已反馈，待最终执行证据）

初版恢复逻辑只核对已完成 receipt 的配置、源码和产物哈希；活跃尝试尚无终态 output_hashes 时会被跳过，从而可能在同一输出根目录重复执行同一任务。协议的中断恢复要求包括真实进程状态及产物范围检查，单靠 receipt 不满足这一点。

**修复门槛：** 用同一 OS 跨进程锁覆盖“扫描活跃 manifest → 写入新尝试的完整计划与进程身份”，避免先扫描再无锁登记的竞态。同一输出根目录中重叠 job ID 必须互斥，即使配置哈希变化也不能绕过；不重叠任务可并行。Windows 进程身份需包含实际创建时间，区分 PID 复用；无法确认权限或身份时拒绝，不能猜测进程死亡，也不能用 `os.kill(pid, 0)` 进行 Windows 探活。要求真实子进程、并发登记、已退出、身份不确定和 PID 复用反例。

已只读核对新增源码的 OS 短锁、Windows `OpenProcess/GetProcessTimes` 与全计划原子登记结构；初步未发现登记竞态。原全矩阵尝试须因源码变化明确失败/保留 partial，不能把该版本的局部结果追认为新门禁版本的完整证据。最终定向测试及新版本全矩阵仍待完成。

**进程测试复核：** 第一次独立运行4个新用例，2 failed、2 passed、6 deselected，20.78秒。失败揭示 Windows `.venv` 启动器的 `Popen.pid` 与实际 Python `os.getpid()` 不同，例如13200与28696；测试夹具错误地把启动器PID和实际进程创建身份混用。生产登记使用运行者自己的 `os.getpid()`，不受该夹具错误影响。修复后全部按子程序报告的实际PID核对，异常锁释放用实际持锁 Python 的 `os._exit(1)`，避免只结束启动器后由管道关闭造成正常退出。

第二次独立运行4 passed、6 deselected、23.23秒、exit0。覆盖真实活跃与正常退出、不同任务范围、旧创建时间模拟PID复用、未知/权限不确定拒绝、双进程同时登记仅一方进入实际任务，以及异常进程退出后OS锁释放。执行前后源码哈希不变：checker=`479c1a716ef77c42b0f97c2eddb1e26612abcd938c584a3d6de009db6d0c2765`；测试=`1a62bd02854ecec28291f46515d9421582dff8fe5287e640a7e4ae8ab142f623`。此项门禁通过，最终全矩阵仍须绑定新checker。

### C-R09 异常注入选中数被误当作数值改变数（20万代表发现，待修复）
