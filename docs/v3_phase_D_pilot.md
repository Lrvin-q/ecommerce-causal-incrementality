# Phase D 资源 pilot 与算力外推（6 类作业子集）

> 合成数据 / 已知 DGP。维护时间：2026-10-28 21:35（北京时间）。**历史值声明**：§5–§10 的 1,402/1,186 CPU·h、§7/§8 的 1,402 与 8.4 GB 读数、§10.2 的 8.4 GB 预估、§5/§9 的内存读数，均为 2026-10-25 至 10-27 的历史材料；当前排期口径与内存判据以 §11 为准。
> 本文只记录**实测与算术**，不构成任何科学结果；正式实验 R 仍为 0。

## 1. 为什么要先做这件事

冻结矩阵（`configs/v3/scenarios.yaml` 的 `planned_counts`）是按"批"计数的：7300 个完整学习批、7300 个独立验证批、4000 个完整 AA、2000 个额外功效作业、800 个再训练 bootstrap。要把它们换算成工期，必须知道**每批里各阶段各花多少**。

A 阶段给的"40–55 CPU·h / 8–12 小时墙钟"是估算，交接明确要求：**D 前必须实测，超过原估算 50% 就要重商，未获回复不得削减 N/R**。

## 2. 方法与纪律

三种粒度（同一次 rep 内分别计时，避免重复 I/O 污染）：

| 粒度 | 含义 | 包含阶段 |
|---|---|---|
| **G1 纯估计** | 观测表已就绪，只做学习 | 特征变换 + ITT + 常数/T/S/CF 四模型拟合 + 预测 |
| **G2 五表SQL+估计** | 再加数据工程 | G1 + 生成 + 污染/清洗 + SQL + 观测表 |
| **G3 含CF完整流程** | 再加决策 | G2 + 贪心 + 局部改进策略选择 |

计量：`time.process_time()`（进程 CPU）、`time.perf_counter()`（墙钟）、`psapi!GetProcessMemoryInfo` 的 `PeakWorkingSetSize`（峰值工作集）。模型超参严格取自 `configs/v3/models.yaml`（LightGBM 300 棵、CF 300 棵 / `cv=3` / `min_samples_leaf=60` / `n_jobs=1`）。

不读真值，不写 `data/v3` 或 `audit/v3`；每次 rep 后立即删除流水线目录。脚本：`scripts/13_v3_pilot.py`。

## 4. 瓶颈定位：`_load_facts` 用 Python 生成器逐行插入

`cProfile` 单次 200k pipeline（223 s，含插桩开销）：

| 位置 | 累计秒 | 占比 | 说明 |
|---|---|---|---|
| `run_sql_pipeline` | 144.7 | 62% | 调 2 次（raw + clean） |
| └ `_load_facts` | 100.3 | 43% | **装载事实表** |
| └ `executemany` | 99.2 | — | **366 次调用搬 365 万行** |
| └ `v3_sql.py:117 <genexpr>` | 77.4 | — | 纯 Python 逐行生成元组 |
| └ `pandas ArrowArray.__iter__` | 17.1 | — | 被调 **1,065 万次** |
| `validate_tables` | 59.7 | 26% | 8 次调用，含事件校验 27.5 s |
| └ `deduplicate_events` | 20.7 | 9% | |
| `inject_dirt` | 15.6 | 7% | |

**结论：43% 的时间花在"把 DataFrame 逐行搬进 SQLite"上。** 这是典型的反模式——把 Arrow 列式数据逐元素迭代成 Python 元组。改为 `DataFrame.to_sql(method="multi")`、或先落 Parquet 再用 SQLite 批量导入、或用 `numpy` 一次性构造参数列表，预期可降到 1/3～1/5，即 **170 s → 50–70 s**。

该优化**不改变任何数据与结果**（同样的表、同样的 SQL、同样的行），但必须重跑 C 的 SQL/质量测试与代表库核对作为回归证据。

## 6. 与原估算的对比 —— 一个更根本的问题

| 口径 | CPU·h | 相对原估算（40–55） |
|---|---|---|
| 原估算（A 阶段） | 40–55 | 1× |
| 本次实测外推 | **≈ 1,402** | **25.5–35 倍** |

但真正的问题不是"估少了"，而是**原估算与冻结矩阵在算术上不可能同时成立**：

> 7300 个完整学习批，若总预算只有 40–55 CPU·h，则每批只能分到 **20–27 秒**；
> 而单个 20 万人批**仅数据工程就要 170 秒、加 CF 要 312 秒**。
> 也就是说，40–55 小时这个数在 A 阶段冻结矩阵的那一刻就已经不可能，与本次测量是否精确无关。

这一条应写进 A 阶段的复盘：**先冻结矩阵、后估算资源，且没有用量级校核**，是流程缺陷，不是测量误差。

## 7. 可选路径

| 方案 | 内容 | 估算 CPU·h | 墙钟（4 路并行） |
|---|---|---|---|
| **A 全量照跑** | 冻结矩阵不动，后台长跑 | ≈ 1,402 | ≈ 14.6 天 |
| **B 先优化再跑（建议）** | 修 `_load_facts` 批量插入，重测 pipeline，再按新数字排期 | ≈ 810（乐观） | ≈ 8.4 天 |
| **C 缩减范围** | 需用户显式批准并写入协议；例如把外围格 R 由 100 降到 50、或减少独立验证批数 | 按缩减比例 | 相应缩短 |
| **D 分层交付** | Tier1 核心格全量先跑完并出结果，Tier2 外围格后置/最简 | Tier1 约占 1/3 | ≈ 5 天出核心结果 |

**我建议 B + D 组合**：先做 `_load_facts` 优化（预计省 40%），再把 Tier1 核心格与 Tier2 外围格分开排期，核心结果先落地。但这需要用户确认，因为 B 会改 `v3_sql.py`（属于 B/C 阶段已冻结的源码范围，需要重跑回归并重新绑定源码 hash）。

## 8. 未决与风险

1. 上述 1,402 h 未包含两个歧义项，也**未包含** `model_mode_jobs 49,300` 与 `learner_fit_calls 64,500` 的独立展开——若它们是 7300 学习批之外的新增作业，总量会显著更高。需要在 A 的计数口径上再确认一次。
2. ~~并行上限受内存约束（1.88 GB/rep，可用 8.4 GB）~~ —— **2026-10-28 21:20 按 §11.2 更正**：8.4 GB 是 2026-10-25 16:10 的会话读数，不是 pilot 测量；新鲜进程单 rep 峰值为 1.79–1.89 GiB，同进程 20 rep 的运行最大值为 2.62 GiB。并行度按内存实读与 CPU 占空比决定（§11.2），本句不再作为“4 路不可行”的依据。
3. `_load_facts` 优化会触及已冻结源码（`v3_sql.py`），必须重跑 C 的 800 项回归与四代表库逐行核对，并重新绑定源码 hash——**这是"优化"而不是"改机制"，但不能省掉回归**。
4. 本 pilot 只测了 L1_main。L2/L3 的单批成本预计与 L1 同量级（同样的 20 万人五表 + 同样的 CF），但未实测；按协议应在 D 中补测至少 L0 与 L3 各 1 rep（**2026-10-28 18:57 已补测 L0/L3 各 1 rep，结果见 §11.4**；L2 仍未实测）。

### 11.2 内存：进程级峰值与累积水位

进程级峰值均值 **2,593.67 MiB**、最大 **2,682.36 MiB**（= 2.62 GiB = 2.81 GB 十进制；rep 8 起）。逐 rep 轨迹：
rep 0 为 1,870.98 MiB → rep 5 2,620.45 MiB → rep 8–19 恒为 **2,682.36 MiB**。

### 11.5 局限与结论失效条件

- **单机、单场景、单版本**：20 rep 只测 L1_main；L0/L3 各 1 rep；n = 200,000；同进程暖态；无并发。换机器、换 n、换源码版本或并发运行后，单批秒数即失效。
- **内存只记录运行最大值**：`PeakWorkingSetSize` 无法还原逐 rep 的常驻 RSS；>20 rep 的水位未测，长跑必须复位与监控（决策日志 2026-10-25 15:56）。
- **CPU/墙钟 0.9617 是单进程比值**：它不能证明 3/4 进程线性、不换页；并行墙钟是算术折算，不是并行实测。
- **外部沿用值**：`retraining_bootstrap` 的 476.1 s 来自 §9，未重测；5 类未计入计数的成本未测（§11.3）。
- **用途边界**：本节只用于排期，不构成任何科学结果；不据此削减任何 N/R。
