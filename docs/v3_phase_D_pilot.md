# Phase D 资源 pilot 与全矩阵算力外推

> 合成数据 / 已知 DGP。维护时间：2026-10-25 10:52（北京时间）。
> 本文只记录**实测与算术**，不构成任何科学结果；正式实验 R 仍为 0。

## 1. 为什么要先做这件事

冻结矩阵（`configs/v3/scenarios.yaml` 的 `planned_counts`）是按"批"计数的：7300 个完整学习批、7300 个独立验证批、4000 个完整 AA、2000 个额外功效作业、800 个再训练 bootstrap。要把它们换算成工期，必须知道**每批里各阶段各花多少**。

A 阶段给的"40–55 CPU·h / 8–12 小时墙钟"是估算，交接明确要求：**D 前必须实测，超过原估算 50% 就要重商，未获回复不得削减 N/R**。

## 2. 方法与纪律

三种粒度（同一次 rep 内分别计时，避免重复 I/O 污染）：

| 粒度 | 含义 | 包含阶段 |
|---|---|---|
| **G1 纯估计** | 观测表已就绪，只做学习 | 特征变换 + ITT + 常数/T/S/CF 四模型拟合 + 预测 |
| **G2 五表SQL+估计** | 再加数据工程 | G1 + 生成 + 污染/清洗 + SQL + 观测表 |
| **G3 含CF完整流程** | 再加决策 | G2 + 贪心 + 局部改进策略选择 |

计量：`time.process_time()`（进程 CPU）、`time.perf_counter()`（墙钟）、`psapi!GetProcessMemoryInfo` 的 `PeakWorkingSetSize`（峰值工作集）。模型超参严格取自 `configs/v3/models.yaml`（LightGBM 300 棵、CF 300 棵 / `cv=3` / `min_samples_leaf=60` / `n_jobs=1`）。

不读真值，不写 `data/v3` 或 `audit/v3`；每次 rep 后立即删除流水线目录。脚本：`scripts/13_v3_pilot.py`。

## 4. 瓶颈定位：`_load_facts` 用 Python 生成器逐行插入

`cProfile` 单次 200k pipeline（223 s，含插桩开销）：

| 位置 | 累计秒 | 占比 | 说明 |
|---|---|---|---|
| `run_sql_pipeline` | 144.7 | 62% | 调 2 次（raw + clean） |
| └ `_load_facts` | 100.3 | 43% | **装载事实表** |
| └ `executemany` | 99.2 | — | **366 次调用搬 365 万行** |
| └ `v3_sql.py:117 <genexpr>` | 77.4 | — | 纯 Python 逐行生成元组 |
| └ `pandas ArrowArray.__iter__` | 17.1 | — | 被调 **1,065 万次** |
| `validate_tables` | 59.7 | 26% | 8 次调用，含事件校验 27.5 s |
| └ `deduplicate_events` | 20.7 | 9% | |
| `inject_dirt` | 15.6 | 7% | |

**结论：43% 的时间花在"把 DataFrame 逐行搬进 SQLite"上。** 这是典型的反模式——把 Arrow 列式数据逐元素迭代成 Python 元组。改为 `DataFrame.to_sql(method="multi")`、或先落 Parquet 再用 SQLite 批量导入、或用 `numpy` 一次性构造参数列表，预期可降到 1/3～1/5，即 **170 s → 50–70 s**。

该优化**不改变任何数据与结果**（同样的表、同样的 SQL、同样的行），但必须重跑 C 的 SQL/质量测试与代表库核对作为回归证据。

## 5. 全矩阵外推

按 `planned_counts` 的批数 × 实测单批成本：

| 作业类型 | 批数 | 单批构成 | 单批秒 | **合计 CPU·h** |
|---|---|---|---|---|
| `historical_dgp_jobs` | 12,500 | DGP | 2.0 | 6.9 |
| `full_learning_data_jobs` | 7,300 | G3 + DGP | 311.9 | **632.5** |
| `independent_validation_jobs` | 7,300 | DGP + pipeline | 171.7 | **348.2** |
| `complete_aa_jobs` | 4,000 | DGP + pipeline + ITT | 172.7 | 191.9 |
| `additional_design_power_jobs` | 2,000 | DGP + pipeline + 轻估计 | 174.0 | 96.7 |
| `retraining_bootstrap_jobs` | 800 | DGP + pipeline + 8.5 次拟合 | 568.2 | 126.3 |
| **合计（不含下述歧义项）** | | | | **≈ 1,402 CPU·h** |

墙钟：按 5 路并行 ≈ **280 小时 ≈ 11.7 天**；6 路 ≈ 234 小时 ≈ 9.7 天。峰值内存 1.88 GB/rep，6 路并行约 11.3 GB，**超过本机可用的 8.4 GB**，实际并行上限约 **4 路**（→ 350 小时 ≈ 14.6 天）。

### 两个口径歧义（必须由用户或 A 阶段澄清）

| 项 | 计数 | 歧义 |
|---|---|---|
| `random_baseline_lists` | 11,680,000 | 是"11.68M 个用户条目"还是"11.68M 次完整名单抽取"？若是后者（每次 20 万用户约 20 ms），将额外增加 **≈ 65 CPU·h** |
| `budget_risk_predictive_resamples` | 7,300,000 | 同上量级问题 |

这两项在现有 CSV 里没有单次成本的落盘记录，本次 pilot 未覆盖，**不得当作已计入**。

## 6. 与原估算的对比 —— 一个更根本的问题

| 口径 | CPU·h | 相对原估算（40–55） |
|---|---|---|
| 原估算（A 阶段） | 40–55 | 1× |
| 本次实测外推 | **≈ 1,402** | **25.5–35 倍** |

但真正的问题不是"估少了"，而是**原估算与冻结矩阵在算术上不可能同时成立**：

> 7300 个完整学习批，若总预算只有 40–55 CPU·h，则每批只能分到 **20–27 秒**；
> 而单个 20 万人批**仅数据工程就要 170 秒、加 CF 要 312 秒**。
> 也就是说，40–55 小时这个数在 A 阶段冻结矩阵的那一刻就已经不可能，与本次测量是否精确无关。

这一条应写进 A 阶段的复盘：**先冻结矩阵、后估算资源，且没有用量级校核**，是流程缺陷，不是测量误差。

## 7. 可选路径

| 方案 | 内容 | 估算 CPU·h | 墙钟（4 路并行） |
|---|---|---|---|
| **A 全量照跑** | 冻结矩阵不动，后台长跑 | ≈ 1,402 | ≈ 14.6 天 |
| **B 先优化再跑（建议）** | 修 `_load_facts` 批量插入，重测 pipeline，再按新数字排期 | ≈ 810（乐观） | ≈ 8.4 天 |
| **C 缩减范围** | 需用户显式批准并写入协议；例如把外围格 R 由 100 降到 50、或减少独立验证批数 | 按缩减比例 | 相应缩短 |
| **D 分层交付** | Tier1 核心格全量先跑完并出结果，Tier2 外围格后置/最简 | Tier1 约占 1/3 | ≈ 5 天出核心结果 |

**我建议 B + D 组合**：先做 `_load_facts` 优化（预计省 40%），再把 Tier1 核心格与 Tier2 外围格分开排期，核心结果先落地。但这需要用户确认，因为 B 会改 `v3_sql.py`（属于 B/C 阶段已冻结的源码范围，需要重跑回归并重新绑定源码 hash）。

## 8. 未决与风险

1. 上述 1,402 h 未包含两个歧义项，也**未包含** `model_mode_jobs 49,300` 与 `learner_fit_calls 64,500` 的独立展开——若它们是 7300 学习批之外的新增作业，总量会显著更高。需要在 A 的计数口径上再确认一次。
2. 并行上限受内存约束（1.88 GB/rep，可用 8.4 GB），不是受核数约束。若要提高并行度，必须先降低单 rep 内存（例如 pipeline 分块、SQL 分段提交）。
3. `_load_facts` 优化会触及已冻结源码（`v3_sql.py`），必须重跑 C 的 800 项回归与四代表库逐行核对，并重新绑定源码 hash——**这是"优化"而不是"改机制"，但不能省掉回归**。
4. 本 pilot 只测了 L1_main。L2/L3 的单批成本预计与 L1 同量级（同样的 20 万人五表 + 同样的 CF），但未实测；按协议应在 D 中补测至少 L0 与 L3 各 1 rep。

## 9. 多 rep 复核（2026-10-25 11:02，北京时间，追加）

首跑（rep 0，独立进程，含冷启动）与随后 3 个 rep（同一进程顺序执行）差异明显，**以 3 rep 均值为准**：

| 阶段 | rep 0（冷） | rep 1–3 均值 | 差异解释 |
|---|---|---|---|
| DGP | 2.0 s | 0.85 s | 首次导入/编译 |
| **五表SQL** | 169.7 s | **143.7 s** | SQLite 页缓存与连接复用 |
| **Causal Forest** | 133.4 s | **116.6 s** | LightGBM 首次构建 |
| G1 纯估计 | 140.2 s | 122.1 s | |
| **G3 含CF完整** | 309.9 s | **265.8 s** | |
| 墙钟 | 321.5 s | 275.8 s | CPU/墙钟 ≈ 0.96 |

**内存要注意**：`PeakWorkingSetSize` 是**进程级**峰值，不是单 rep 峰值。rep 0 独占进程时 1,878 MB；3 个 rep 顺序跑在同一进程时升到 **2,471 MB**，说明顺序执行有内存累积。**正式编排应一个 rep 一个进程**，否则并行度会因累积内存而被迫下调。

**结论未变：约 1,190 CPU·h（区间 1,190–1,400，取决于冷启动比例），仍是原估算 40–55 的 22–30 倍。**

墙钟按单 rep 独占进程、4 路并行（受 8.4 GB 可用内存约束）：≈ **297 小时 ≈ 12.4 天**；若优化 `_load_facts` 后 pipeline 降到 60 s，则 ≈ **730 CPU·h ≈ 7.6 天**。

## 10. D01 正式 20 rep 计划（2026-10-27 20:33，北京时间，待授权）

D01 验收要求 **20 rep 三粒度实测**；现有实测只有 **3 rep（rep 1–3）**，且只覆盖 L1_main。
本节只写执行计划与算术，**未开跑**；`R=20 > 0`，须用户显式批准后才能启动。

### 10.1 运行编排

- 主作业：`scripts/13_v3_pilot.py --reps 20 --n 200000`（L1_main）。
- 进程切分：文档 §9 已实测**同进程顺序执行会累积内存**（1,878 MB → 2,471 MB），
  因此按 **4 进程 × 5 rep** 执行，每个进程一个独立 Python，避免 20 rep 单进程把峰值推到不可控。
- 场景补测：按 §8.4，另跑 **L0、L3 各 1 rep**（n=200 000，三粒度），用于支撑"单批成本跨层同量级"的外推；
  这两 rep 只作资源证据，不进入任何科学结果。
- 产物：`out/v3_phase_d/`（明细 CSV + summary JSON + profile），并导出汇总到
  `outputs/tables/v3_phase_D_pilot_raw.csv` 与 `outputs/tables/v3_phase_D_pilot_summary.json`（覆盖现有 3 rep 版本前先保留旧文件为 `*_3rep.*`）。
- 运行期间不写 `src/ sql/ configs/`；pilot 不读真值、不写 `data/v3` / `audit/v3`。

### 10.2 资源估算（按 3 rep 均值 275.8 s/rep）

| 项 | 估算 | 依据 |
|---|---|---|
| L1_main 20 rep 墙钟 | ≈ 92 分钟（4 进程 × 5 rep，单进程串行） | 20 × 275.8 s ≈ 5,516 s |
| L0/L3 各 1 rep | ≈ 10 分钟 | 2 × 275.8 s ≈ 552 s |
| 合计墙钟 | **≈ 1.7 小时** | 不含冷启动与失败重试 |
| CPU 时间 | **≈ 1.6 CPU·h** | 20 × 266 s + 2 × 266 s ≈ 5,852 s |
| 峰值内存 | 单进程 ≈ 2.5 GB；4 进程并行 ≈ 10 GB | 可能超过当前可用 8.4 GB，**实际按 3 进程并行** |
| 磁盘 | < 200 MB | 每次 rep 删流水线目录，只留 CSV/JSON |

并行度按 **3 进程**重新估算：20 rep ≈ 7 批 × 276 s ≈ **32 分钟**；加上 L0/L3 ≈ **40 分钟**。

### 10.3 D01 验收口径

1. `failed = 0`，20 个 rep 的 G1/G2/G3 三粒度均有完整计时；
2. 报告 **均值、sd、最小/最大**，不只报均值（AGENTS §12.5：相对差报最差格）；
3. 内存按进程级峰值报告，并注明"单进程独占 vs 同进程累积"两种口径；
4. 用 20 rep 均值刷新 §5/§9 的全矩阵外推，给出 CPU·h 区间与并行墙钟；
5. L0/L3 单 rep 与 L1 的单批成本对照，若差异 > 50% 必须在报告中说明；
6. 报告的"资源计划"只用于排期，**不得据此削减任何 N/R**。
