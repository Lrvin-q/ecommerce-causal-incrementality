## 2026-10-25 11:15（北京时间）编排教训：并行写 v3*.py 会触发源码绑定门禁的假红

- 现象：四个代理并行开发期间，`tests/test_v3_pipeline.py` 与 `test_v3_data_checks.py` 报 `RuntimeError: source files changed during the data run; retain this attempt as failed`。
- 根因：`pipeline_source_hashes()` 在 `build_observed_pipeline` 前后各哈希一次 `src/causal_growth/**/v3*.py`、`sql/v3*.sql`、`configs/v3*.yaml`；任何代理在别人跑 pipeline 期间新建/修改 `v3*.py`，都会让"产物绑定源码快照"这项检查判伪。**门禁是对的，错的是并行编排。**
- 处置（不削弱门禁）：
  1. 代理只对**自己的**测试文件负责；全套"803 全绿"由主控在所有代理停写后**单进程串行**跑一次。
  2. 允许在测试里对**这一个特定异常**做 `pytest.skip`，但必须在报告里列出被跳过项，不许吞其它失败。
  3. 需要跑全链路的基准/等价性测试，改用不经过前后哈希的入口（`run_sql_pipeline`），既稳定又更聚焦。
  4. 任何人不得为绕开门禁去改 `v3_pipeline.py`。
- 启示：**并行开发的粒度要按"写盘冲突"而不是按"任务大小"来切**。本项目里 `v3*.py` 的全目录哈希把"四个互不相关的模块"耦合成了同一个临界区——这与 AGENTS §7.5"按目录/模块划分归属"看似一致、实则不够：真正的边界是"是否被同一个哈希门禁覆盖"。
- 后续 G 阶段正式重复时，编排器必须保证**一个 rep 一个进程、且运行期间源码只读**；否则同样的假红会出现在正式结果里。

## 2026-10-25 11:52（北京时间）D 阶段两项裁决 + D.1/D.3 验收
