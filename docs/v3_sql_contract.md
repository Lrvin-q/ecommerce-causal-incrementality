# v3 SQL 观测核算契约

> 合成数据 / 已知 DGP。Phase C 工程实现与校验；本文件不表示正式 R 已完成。

## 1. 执行入口与五表边界

`run_sql_pipeline(tables, cfg, *, database_path=None, asof_day=None, relative_snapshot_days=None, allow_immature=False)` 接受五个 DataFrame：`users`、`coupon_assignment`、`user_events`、`orders`、`user_outcomes`。未知表、未知字段、缺字段、重复字段名均拒绝。用户与分配采用 `(run_id,user_id)` 联合主键；订单和行为事件也以 `run_id` 参与主键、外键和所有连接，避免重复间相同用户 ID 错连。

主分析严格来自 `sql/v3_analytics.sql` 的物化 `user_outcomes` 和分析视图。生产模块 `data/v3_sql.py` 不导入 B 阶段的数组账本或潜在世界。独立数组账本只在测试中作为对账对象。输入的 `user_outcomes` 即使已包含行，也会从事实四表重新核算，绝不把旧派生值当作分析输入；结果中的 `recomputed_input_outcomes` 明示这一行为。

不传数据库路径时使用 SQLite 内存库，传路径时保存完整数据库；两者执行同一 DDL、同一参数视图、同一核算 SQL 与质量查询。已有数据库文件不会被覆盖。失败尝试的数据库由上层运行记录标为失败，不充当成功产物。

数据库恰有五张业务表。`v3_parameters`、`v3_policy_design`、`v3_known_channels` 是配置元数据视图，不是额外业务表；其他对象是核算或汇总视图。每次连接启用 `PRAGMA foreign_keys=ON`，DDL 使用 STRICT 类型及 PK/FK/CHECK；外部重新打开数据库并写入时也必须在该连接启用外键检查，这是 SQLite 的连接级设置。

## 2. 时间、可见分母和成熟

全部时间使用合成相对日；小时到日的换算来自 `configs/v3_data.yaml`，不在代码写业务常量。窗口长度来自冻结业务配置，窗口名称来自工程配置，边界均包含等号。

完整模式的默认截止时刻是最晚分配日加利润窗口与配置的最大入库延迟。必须保留输入的全部分配用户，并且每人的利润窗口已完全成熟；任一条件不满足即拒绝主分析。退款、未支付、未核销和负利润用户不参与任何排除条件。正式运行器还须将这里的 `input_users_n` 与该批生成元数据及登记人数对照，SQL 无法仅凭一组已经被上游删过人的表推断原始人数。

诊断提供两种互斥时钟：

- `asof_day`：绝对快照。只纳入分配已经发生且分配记录已经入库的用户，不能把未来的用户、标签与特征加入过去的分析。
- `relative_snapshot_days`：每用户分配后固定天数的快照，`effective_asof=assignment_day+relative_snapshot_days`。用于 L2 的分配后短窗口误用对照，不能用“最晚分配日加同一天数”代替。

相对快照必须显式传入 `allow_immature=True`。任何非完整分析也必须显式标诊断；它记录原输入人数 `input_users_n` 和当时可见分配人数 `visible_assigned_n`，而不是把两者混称为全体分配人数。诊断的全部结果行带 `diagnostic_snapshot=1`，不能因某部分用户已成熟便自动升级为正式主分析。

每个窗口保留 `complete_after_day=assignment_day+(window_days+maximum_ingestion_delay_days)`。默认截止与相对快照均先相加时长再加分配时钟，避免浮点加法结合顺序使精确 32 天端点被误判为未成熟。`mature` 必须满足截止时刻不早于这个保守完成时刻；不使用时间容差，不把截止移到 32.1 天。

闭端点采用明确的 binary64 运算约定。物化前先验证每条分配、行为、支付、退款的 `event_day <= raw_ingested_day <= event_day+maximum_delay`，上界直接相加比较，禁止用相减后的延迟比较。窗口事件条件仍严格比较 `assignment_day <= event_day <= assignment_day+window_days`。在 `asof_day >= complete_after_day` 时，已验证的最大延迟保证所有窗内事件可用，因此支付和退款均按完整到数处理；尚未成熟的快照仍严格使用原始入库时刻。这同时处理 `(assignment_day+window_days)+delay` 与 `assignment_day+(window_days+delay)` 的两种舍入方向，不放行窗口终点之后的事件，也不放行事件自身最大入库端点之后的非法到达。

`required_ingestion_day` 是当前可见分配及窗内可见支付/退款的**窗口规范可用时刻**最大值：每项按 `min(raw_ingested_day, complete_after_day)` 映射后取最大值。这个映射只应用于已经通过事件窗口和入库上界门禁的贡献；它不与 `asof_day` 取最小值，不能将未成熟快照中的未来事件提前。原始事实表的入库时间保留不变；在端点处，它可能因加法结合次序比规范时刻晚 1 ULP。尚不可见的未来退款不进入此字段；不能仅凭“目前最后一条记录已经到达”声称窗口完整。滚动训练须同时检查窗口结束、保守完成时刻和规范可用时刻。

绝对诊断的 `user_outcomes` 行数为可见人数的两倍，可能少于输入用户表的两倍；完整成熟模式两者相同。用户事实表保留全输入，SQL 只对快照可见人群生成当时结果。

## 3. 两窗口与整数分核算

`user_outcomes` 每可见用户、每窗口一行。两窗口各自按其结束时刻核算，不把利润窗口的退款状态复制到转化窗口。`v3_analysis` 取转化窗口的 `converted` 作为 `paid_purchase_7d`，取利润窗口的全部金额与退款指标；字段显式区分窗口。

每条支付记账进入某窗口需同时满足：支付事件日在分配日至窗口结束之间、事件已经发生、支付记录按上述窗口时钟已经可用。退款组件使用退款事件日及退款入库日独立判断。单个订单存在于完整事实表不等于它所有未来状态已经对当前快照可见。

支付时记入商品总额、商品成本、履约成本、初始券成本和消费者实付；窗口内可见退款记入商品总额冲减、商品成本回收、退款手续费、消费者退款与退券。两个退款金额和商品总额分别命名。所有组件先以整数分求和，再使用以下 SQL 恒等式：

\[
C_{coupon}=C_{initial}-C_{return},\qquad
\Pi=G-G_{refund}-C_{goods}+C_{recovery}-C_{fulfill}-C_{coupon}-C_{fee}.
\]

元单位列仅在最终投影时除以配置的每元分数，净利润不再次扣券。净交易额为商品总额减商品退款冲减；`gmv` 明确等于券前商品总额，不能称消费者实付或净利润。

在诊断快照中，退款入库可能早于对应支付入库。SQL 保留这一入库异序，允许暂时出现退款订单数大于已入库支付订单数、净券成本为负等中间账态，而不伪造先后或用付款可见条件屏蔽已到达退款。完整成熟结果必须与独立账本逐组件相等。真正从未购买的人仍为零利润；“付款尚未入库”不等于“从未购买”。

跨窗口支付和退款一直保留在 `orders` 中，只有记账贡献按窗口筛选。复购首单关系、券上限和合法退款字段由质量查询与约束检查；复购金额使用由配置十进制比例导出的整数有理数 half-up 校验，避免二进制半分误差。

## 4. 分组与字段白名单

`label` 是分析分组；`treatment` 明确等于它。常规历史实验中它等于 `actual_action`，真正 AA 使用独立虚拟标签但实际动作固定为零。独立政策验证中 `label/treatment` 为政策臂，`actual_action` 仍是实际发券动作。政策臂 ITT 分母包含该臂所有分配用户，不换成实际发券者数。

随机历史记录 `design_probability`；L3 观察性历史只允许缺省，真实倾向不能进入该列。政策验证使用单独的 `policy_arm_probability`，不能冒称个体发券概率。

完整分析字段的唯一机器契约为 `v3_sql.ANALYSIS_COLUMNS`；五表逐字段含义见 [v3 数据字典](v3_data_dictionary.md)。其内容包括观测特征、分配/时间/拆分元数据、两个窗口指标、整数分组件及最终元单位指标。购物车唯一事实源为 `cart_value_cent`，分析时派生 `cart_value`；缺失值保留给训练期拟合的预处理，不在 SQL 中用全量数据填补。记录的 `event_retained_count/event_truncated_count` 不能被说成完整浏览日志。

根部 `ObservedDataset` 还须限制可用于模型的列。存在于分析表的结果字段、成熟时间及入库元数据并不因此成为合法的分配前预测特征。

## 5. 质量与汇总

DDL 检查整数分、金额非负原子组件、消费者实付/退款关系、退款状态与时间一致、首单专属券、联合主外键。SQL 质量查询进一步检查全用户分配覆盖、动作/标签与设计概率、实际券面额、政策臂概率、订单动作与分配时间、已知购物车上限、复购首单/金额/时序、双窗口数、可见分母、零记账恒等式、事件去重计数、配置入库上界、退券规则和已知渠道。失败抛出异常，不能仅写警告后继续。

输出 `summaries` 包含按组、渠道、新老客、分配周的全体用户汇总，以及 `cost_ledger` 和 `funnel`。支付率与用户级退款率均以全体对应分组用户为分母，订单计数另外列出；退款订单仍参与利润与成本账。分流人数与记录设计概率保留供后续设计检查，这些 SQL 汇总本身不冒称已做 AA 或覆盖率检验。

## 6. 固定溯源与验证边界

`SqlAnalysisResult` 在创建时固化 `config_hash`、`data_config_hash`、`sql_sha256`、`analysis_sha256`。最后一个使用统一的 DataFrame 指纹算法，覆盖有序字段、dtype 与值；后续修改 DataFrame 不会自动更新已经保存的指纹。把真值伪装写入一个合法字段也会使复核失败。持久化层另核文件哈希，不能只相信内存对象类型。

SQL 来源哈希覆盖 DDL、核算 SQL 与执行模块。参数、窗口及诊断模式留在参数视图和返回元数据中。内存与持久库的一致性、四层污染清洗后与独立账本的逐分一致性、零单用户、退款/复购/跨窗、退券只计一次、绝对与相对快照、未来退款不可见、入库异序、AA/政策臂分母、非法主外键、未知真值字段以及指纹篡改，均在 `tests/test_v3_sql.py` 验证。

这些是工程验收，不替代所有场景代表产物、正式重复、模型识别、策略评估或随机验证。全场景落盘与独立复审由主控统一完成。
