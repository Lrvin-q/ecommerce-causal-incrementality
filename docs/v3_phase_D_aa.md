# Phase D D.2：完整 DGP 链路的 AA（随机化有效性）校验

> 合成数据 / 已知 DGP。维护时间：2026-10-25 12:48（北京时间）。
> 本文只回答"这套链路在真无效应时的错误率与成本"，**不推进正式 R**（`formal_repetitions_completed` 仍为 0）。
> 所有数字来自 `outputs/tables/v3_phase_D_aa.csv`（逐 rep 明细在 `out/v3_phase_d_aa/<run>/`）。

## 1. 这一节要证明什么

HITL 修订建议 §7.2 原文：

> 完整 AA 必须走五表、污染/清洗、SQL 及估计流程：**同一处理条件下分配虚拟 A/B 标签，
> 两个标签不改变购买、券成本或退款机制**。原二元/正态 AA 保留为检验模块单测，明确与完整 AA 分开。

这条要求排除了三种"看起来像 AA"的做法：

| 做法 | 为什么不算 | 本项目位置 |
|---|---|---|
| 二元正态玩具 AA（同分布抽样 + t 检验） | 只检验"抽样 + 检验"两步，无法发现五表/污染/SQL 链路把标签变成伪处理变量 | `src/causal_growth/design/aa.py`（单测，**与本文分开**） |
| "购买效应为零但照常发券" | 处理组真的领券并产生补贴成本，利润真值为负；这是负对照，不是利润零效应 | `L0_zero_purchase_effect`（B 阶段审计平均利润 CATE −0.559026 元） |
| 只在最终观测表上重抽标签 | 跳过了清洗/去重/入库延迟/SQL，等于假设这些步骤无害 | 本轮明确不做 |

因此本节的合格证据只有一条：**在四个已注册的 `*_AA` 格上，用同条件虚拟标签跑完整链路，
检验"标签 → 观测利润"的 ITT 是否以 α 的概率误报**。检验本身只看 p 值分布，不看单次 AA 是否显著。

## 2. 设计：虚拟标签怎么贴、为什么不改变机制

### 2.1 四个已注册的无效应主场景

格数不是手抄的：本模块从 `configs/v3/scenarios.yaml` 里取 `formal_repetitions.complete_aa > 0`
的格，并用 `matrix_contract.reference_scenarios` 的层清单核对"每层恰一个"（`aa_cells()`）。

| 层 | 场景 | tier | 注册 n | 注册 R | 实际动作 | 标签概率 | 该层额外覆盖的机制 |
|---|---|---|---|---|---|---|---|
| L0 | `L0_AA` | 1 | 200,000 | 1,000 | 全员 0（不发券） | 0.5 | 同质基线 |
| L1 | `L1_AA` | 1 | 200,000 | 1,000 | 全员 0 | 0.5 | 异质购买概率 + 金额诱导 |
| L2 | `L2_AA` | 1 | 200,000 | 1,000 | 全员 0 | 0.5 | 时间构成 + 窗口成熟 |
| L3 | `L3_AA` | 1 | 200,000 | 1,000 | 全员 0 | 0.5 | 隐藏混淆 U（lambda_Y=0.5） |

四个格都有 `roles` 含 `complete_aa / five_tables / dirty_clean / sql / estimation / truth_audit`，
`models: []`（AA 不拟合模型），`pairing_group` 各自独立。

### 2.2 虚拟标签怎么贴

代码路径在 `src/causal_growth/dgp/v3_probability.py::assign_treatment`（下面为示意，省略了
`override` 与冻结设计的校验）：

```python
if bool(cfg.require("dgp.virtual_aa_labels")):
    override = cfg.require("dgp.actual_action_override")      # = design.aa.actual_action = 0
    probability = float(cfg.require("design.aa.virtual_label_probability"))  # 0.5
    virtual = child_rng(seed, f"{prefix}.assignment.aa_virtual_label", rep_id).random(n)
    action = np.full(n, int(override), dtype=np.int8)         # 全员同一动作
    label  = (virtual < probability).astype(np.int8)          # 只由该流决定
    return AssignmentDraw(action, label, np.full(n, probability), np.full(n, float(override)), None)
```

三个要点：

1. **标签随机流与动作随机流分离**。普通场景读 `{prefix}.assignment.action`；
   AA 读 `{prefix}.assignment.aa_virtual_label`。两条流的 `(master_seed, stream, index)` 不同，
   互不扰动（AGENTS §3.3）。
2. **动作被冻结为常数**，不读任何协变量、不读 U、不读标签。因此不存在"标签影响分配概率"的通路。
3. **结果机制不看标签**：`dgp/v3_engine.py::_world_orders` 的入参只有
   `action / purchase / uniforms / amounts / timing / goods_ratio / redemption_probability`。
   购买、退款、核销、金额、时点全部由 `(X, U, action)` 与各自命名的流决定。

### 2.3 逐项核对：两个标签对应同一机制

| 机制项 | 由什么决定 | 与虚拟标签的关系 |
|---|---|---|
| 购买概率 `p0/p1` | X、U（L3）、`lambda_y`、`purchase_increment` | 无关；两标签同一 `p` |
| 购买/复购事件 | `purchase`、`repeat` 均匀流（`{prefix}.outcomes.*`） | 无关 |
| 首单/复购金额 | 购物车 `Q`、`fraction_draw`（跨动作共享）、重复比例 0.55 | 无关 |
| 核销 | `redemption` 均匀流 × `redemption_probability` × `action` | 两标签 `action` 均为 0 → 核销恒为 0 |
| 退款 | `refund_rate × refund_rate_treated_multiplier^action` | `action=0` → 乘子 1.03 不生效，两标签同率 |
| 履约成本/时点 | `fulfillment`、`order_delays` 流 | 无关 |
| 券面额/券成本 | `coupon_face_cent = actual_action × 面额`（`v3_tables.py`） | 两标签恒为 0 |
| 观察窗/成熟时钟 | `assignment_day + profit_days + max_delay` | 与标签无关 |
| SQL 分析标签 | `v3_analytics.sql`：`a.label AS treatment`，`actual_action` 只驱动券面额 | 标签只出现在 `treatment` 列 |

**结论**：两个标签是同一结果机制下的两次随机分组，因此
`E[Π | label=1] − E[Π | label=0] = 0`、`E[purchase | label=1] − E[purchase | label=0] = 0`
是真值，而不是"假设"。

### 2.4 每个 rep 的链路不变量（代码断言，违反立刻抛）

`run_aa_rep()` 在进链路前后各检查一次，失败抛 `AAChainError`（不吞掉、不继续）：

进入链路前（`_check_assignment_inputs`）：
1. 分配人数 == 请求 n；用户键唯一；
2. 标签同时出现 0/1；
3. `actual_action` 恒等于 `design.aa.actual_action`；
4. 记录的设计概率恒等于 `design.aa.virtual_label_probability`。

走完五表/污染清洗/SQL 后（`_check_observed_chain`）：
5. 观测表人数 == n（R1 分母：随机分配的全部用户，不是支付/核销用户）；
6. 用户集合与生成人群一致、`run_id` 唯一且匹配；
7. **观测表 `treatment` 逐人等于输入的虚拟标签**（不在链路里被改写）；
8. `actual_action` 全为冻结动作、`coupon_cost` 与 `coupon_cost_cent` 恒为 0（券成本没被写进标签）；
9. 全部成熟、无诊断快照、拆分已分配、标签未退化；
10. ITT 的 `n_treated + n_control == 分析人数`（分母没被悄悄换掉）。

这 10 条同时就是"标签没有改变购买/券成本/退款机制"的**可执行定义**：如果链路任何一步
把标签写进动作、券成本或样本选择，6–10 会先炸，而不是给出一个好看的 p 值。

### 2.5 估计与汇总口径

* **主指标** `net_profit`（元/合格用户）→ Welch t（`estimate/itt.py::itt_difference_means`）。
* **诊断指标** `paid_purchase_7d`（购买率）→ 两比例 z；**护栏指标** `any_refund_30d`（30 天内任一单退款的事件率）→ 两比例 z。
  两者角色是 `auxiliary_diagnostic` / `guardrail_diagnostic`，不参与主决策。
* **分析人群**：`full` = 随机贴标签的全部用户（R1 口径，**AA 结论以此为准**）；
  `test` = 冻结 30% 测试拆分上的同一估计（诊断，防止结论只是分拆产物）。
* **假阳性率** = `mean(p < α)`，α 取 `design.alpha_two_sided = 0.05`；
* **区间** = Clopper–Pearson 精确区间（本模块 `clopper_pearson()`，Beta 分位数，双尾等尾）；
* **MC 精度** = `sqrt(p̂(1−p̂)/R)`：有限 R 下 FPR 不可能精确等于 0.05，必须连精度一起报；
* **覆盖率** = 95% CI 是否含 0（AA 下真值为 0）；
* p 值分布另报 `mean_p / median_p` 与对 Uniform(0,1) 的 KS 检验。

**覆盖率读法的硬约束**：对 Welch t，"区间含 0" 与 "p ≥ α" 是同一个事件，
所以 `coverage ≡ 1 − FPR`，它不是独立证据；只有两比例检验（检验用合并方差、CI 用非合并方差）
两者才会略有差别。本文不做"覆盖率另证一遍 AA"的表述。

## 4. 负对照：购买零增量 ≠ 利润零效应

决策 Q2 的原文口径："购买效应为零但发券仍产生补贴成本时，利润效应可能为负，
**这不是"利润零效应 AA"**"。本模块用三列把两种情形机械地分开，避免口头混淆：

| 列 | 真正 AA | 负对照 |
|---|---|---|
| `block` | `true_aa` | `purchase_null_negative_control` |
| `truth` | `0.0`（标签与机制无关，真值就是 0） | 购买率 0.0；**利润与护栏留空**（真值非 0，不填 0） |
| `interpretation` | `false_positive_rate_under_true_null` | `size_under_true_purchase_null` / `power_under_nonzero_profit_truth_not_aa` / `power_under_nonzero_guardrail_truth_not_aa` |
| `coverage` | 报（真值 0） | 利润/护栏**留空**（"区间含 0"在真值非 0 时不是覆盖率） |

负对照跑的是已注册的 `L0_zero_purchase_effect`（`dgp.l0.purchase_increment = 0`，
处理仍发券）。它的购买率真值为 0、利润真值 < 0（B 阶段审计：平均利润 CATE −0.559026 元），
所以：

* 购买率的拒绝率才应该 ≈ α；
* 利润的拒绝率是**功效**（真值非 0），把它读成"假阳性率"就是把负对照当 AA 通过——
  本文显式禁止这种读法，汇总表里该块的 `interpretation` 也不是 AA 口径。

### 5.2 主指标：四层假阳性率（`net_profit`，全部分配用户）

| 层 | 场景 | R | 每组人数 | 假阳性率 | CP95 区间 | MC SE | 覆盖率 | mean p | median p | KS p |
|---|---|---|---|---|---|---|---|---|---|---|
| L0 | `L0_AA` | 50 | 5,004.5 / 4,995.5 | 0.060 | [0.013, 0.166] | 0.034 | 0.940 | 0.479 | 0.456 | 0.827 |
| L1 | `L1_AA` | 50 | 4,989.0 / 5,011.0 | 0.020 | [0.001, 0.107] | 0.020 | 0.980 | 0.565 | 0.625 | 0.182 |
| L2 | `L2_AA` | 50 | 5,011.5 / 4,988.5 | 0.080 | [0.022, 0.192] | 0.038 | 0.920 | 0.534 | 0.585 | 0.610 |
| L3 | `L3_AA` | 50 | 4,997.0 / 5,003.0 | 0.060 | [0.013, 0.166] | 0.034 | 0.940 | 0.467 | 0.431 | 0.405 |
| **合并** | 四层独立 rep | **200** | 5,000.5 / 4,999.5 | **0.055** | **[0.028, 0.096]** | **0.016** | 0.945 | 0.511 | 0.518 | 0.310 |

读法（三条都必须写进任何引用）：

1. **逐层 R=50 几乎不能判定任何事。** 每层的 CP 区间半宽约 0.05–0.09；L2 的 0.080 看起来最高，
   但在 H0（真实 0.05）下 `P(k ≥ 4 | R=50) ≈ 0.24`，它不是"某层链路坏了"的证据。
   四层的 CP 区间**都含 0.05**，但没有一层的区间窄到能支持"该层 FPR 就在 0.05 附近"。
2. **合并行才是有信息量的结论**：200 次里 11 次假阳性，`0.055`，CP `[0.028, 0.096]`，
   MC SE `0.016`。区间含 0.05，也含 0.035–0.065 的验收带；但它同样含 0.028 与 0.096，
   所以正确表述是**"与 0.05 相符、未发现结构性膨胀"**，而不是"证明等于 0.05"。
3. **p 值分布没有异常形状**：mean p = 0.511、median = 0.518、KS 对 Uniform 的 p = 0.310。
   注意 KS 在 R=50/200 下功效很低，它只能排除"极端偏斜"，不能作为通过判据。

`test` 拆分（每组约 1,500 人）上的同一估计：合并 R=200，假阳性率 0.035，CP `[0.014, 0.071]`，
覆盖率 0.965。**结论不依赖"用全量还是用测试拆分"**——两者的 CP 区间都含 0.05。

### 5.4 负对照：同一链路、同一发券机制，只是真值不同

| 指标 | 真值口径 | R | 拒绝率 | CP95 | mean p | 平均 ITT（利润=元/人；率=份额） | ITT 的 95% CI 宽度 |
|---|---|---|---|---|---|---|---|
| `net_profit` | **< 0**（发券有补贴成本） | 50 | **0.940** | [0.835, 0.987] | 0.018 | **−0.578 元/人** | 0.641 |
| `paid_purchase_7d` | **= 0**（`purchase_increment = 0`） | 50 | **0.040** | [0.005, 0.137] | 0.454 | −0.0001 | 0.024 |
| `any_refund_30d` | ≠ 0（`refund_rate_treated_multiplier = 1.03`） | 50 | 0.040 | [0.005, 0.137] | 0.405 | −0.0001 | 0.007 |

这张表就是决策 Q2 的可执行证据：**同一个场景、同一条链路**，购买率的拒绝率是 0.040（真值 0，
所以这是"名义错误率"），利润的拒绝率是 0.940（真值 < 0，所以这是"功效"）。
把后者当"利润零效应 AA 通过/不通过"读，等于把负对照错当 AA——本文明确禁止。

数量级也与 B 阶段的独立审计相符：B 用解析真值算出该格平均利润 CATE 为 **−0.559026 元**
（`docs/v3_phase_B_validation.md`），本文 50 次实现的 ITT 均值是 **−0.578 元**（SE 0.024）。
两者不是同一个量（一个是条件真值均值，一个是有限样本实现的 ITT），但方向与量级一致。

补充：`test` 拆分上利润拒绝率只有 0.520（每组约 1,500 人，功效不足），这说明负对照的"该拒绝"
不是靠大样本硬凑的，也提醒任何用测试拆分做小样本判断的场合都要先看功效。

### 5.5 单次 AA 的 CPU 成本（供 G 外推）

进程 CPU 秒（`time.process_time()`），单线程；**不含**并发写盘造成的重试浪费。

| 规模 | L0 | L1 | L2 | L3 | 均值 |
|---|---|---|---|---|---|
| n=10,000（本文口径） | 10.77 | 9.91 | 7.74 | 8.29 | **9.18** |
| n=200,000（注册规模） | 146.38 | 146.30 | 148.72 | 148.42 | **147.45** |

拆解（n=200,000）：五表 + 污染/清洗 + SQL 占 **144.6–148.3 s（≈99%）**；
DGP 生成 0.25–1.63 s；三个指标 × 两个人群的 ITT 合计 **≤ 0.07 s**。
也就是说，**AA 的成本几乎全部是数据工程，不是估计**——这一点决定了 G 阶段只能靠
pipeline 批量化（`_load_facts`）来省时间，靠"少跑几次 ITT"没有任何意义。

两点定标（(10,000, 9.18) 与 (200,000, 147.45)）给出的经验式：
`单 rep CPU ≈ 1.9 s + 0.73 ms × n`。它是描述性的两点拟合，不是承诺。

**G 阶段外推**：
`4 层 × 1000 次 × 147.45 s = 163.8 CPU·h`；按 4 路并行约 **41 小时墙钟**（不含重试与失败）。
与 D 阶段 pilot 的估算（145.6 s/rep → 161.8 CPU·h）相差 **+1.2%**，两条独立测量互相印证。
但要注意：这是**当前调用点**（`v3_sql.py::_load_facts`）的成本。D.4 已交付 `v3_sql_fast.py` 的批量装载快路径（2.33×）但**尚未切换调用点**；一旦切换，单批会明显低于 147.45 s，G 预算必须按其切换后的实测重算，不能沿用本文数字。
若用户选择 R=1500（§6.3），则约 **245.8 CPU·h**（+50%）。

## 6. 正式 R 的建议值（**不执行**）

### 6.1 先看精度：R 决定 CP 区间能窄到什么程度

假阳性率的估计本身是二项抽样。若真实水平就是 0.05，R 次里期望出现 `0.05R` 次假阳性，
Clopper–Pearson 95% 区间（按期望次数算）与二项 MC 标准误如下：

| R | 期望假阳性次数 | CP95 区间 | 半宽 | MC SE |
|---|---|---|---|---|
| 50 | 2 | [0.0049, 0.1371] | 0.066 | 0.0308 |
| 100 | 5 | [0.0164, 0.1128] | 0.048 | 0.0218 |
| 200 | 10 | [0.0242, 0.0900] | 0.033 | 0.0154 |
| 500 | 25 | [0.0326, 0.0729] | 0.020 | 0.0097 |
| 800 | 40 | [0.0360, 0.0675] | 0.016 | 0.0077 |
| **1000（冻结值）** | 50 | **[0.0373, 0.0654]** | 0.014 | 0.0069 |
| 1200 | 60 | [0.0384, 0.0639] | 0.013 | 0.0063 |
| 1500 | 75 | [0.0395, 0.0623] | 0.011 | 0.0056 |
| 2000 | 100 | [0.0409, 0.0605] | 0.010 | 0.0049 |

（CP 区间由 `clopper_pearson()` 按 `k = round(0.05R)` 计算；R=50/100 两行与本文 §5.2 的实测 R 对照。）

### 6.2 再看功效：R 能排除多大的"结构性膨胀"

GOAL 的假阳性率验收带是 `[0.035, 0.065]`。一个有用的问法是：若流程真有偏（真实 FPR > 0.065），
R 次要多大才能在 80% 功效、单侧 5% 下判定"超界"？

| 真实 FPR | 相对 0.05 的膨胀 | 需要的 R（80% 功效，单侧 5%） |
|---|---|---|
| 0.07 | +40% | ≈ 15,400（实际上不可行） |
| 0.08 | +60% | ≈ 1,800 |
| 0.09 | +80% | ≈ 670 |
| 0.10 | +100% | ≈ 350 |
| 0.12 | +140% | ≈ 150 |

### 6.3 建议（供用户裁决）

1. **Tier 1 维持冻结的 R = 1000／层（共 4000 批）。** 理由：
   * R=1000 时 CP 区间约 `[0.037, 0.065]`，**刚好覆盖验收带 `[0.035, 0.065]`**；
     低于 800 时区间上界会明显越过 0.065，"落在带内"就无法被数据支持（R=500 时上界 0.073）。
   * R=1000 对"膨胀到 0.09 以上"的结构性错误有约 80% 把握判定超界；对 0.08 级别不够（需 ≈1800）。
   * 因此 R=1000 是"能给出可判定结论"的**最小量级**，不是奢侈值。
2. **不建议降低到 R ≤ 200。** R=200 的 CP 区间是 `[0.024, 0.090]`，即使流程完全正确，
   也几乎必然"看起来越界"，报告将无法区分噪声与偏倚——这等于把 AA 变成不能失败也不能通过的仪式。
3. **若要严格证明"整段落在 [0.035, 0.065] 内"，需 R ≈ 1200–1500**（+20%～50% 成本）。
   这是可选项：目前冻结的 1000 已足以支撑"与 0.05 一致、未发现结构性膨胀"的表述，
   但**不应**表述为"假阳性率被证明等于 0.05"。
4. **分层建议**：四层各 1000 次（Tier 1）。若资源受限，**不允许**只跑一层然后外推；
   但允许把 L0（机制最简单）作为先行的 200 次预跑，用于在正式开跑前发现链路错误。
5. 所有正式结果必须带 `R` 与 `MC_SE`；正文引用时必须同时给区间，不得只写点估计。

**本节不执行任何正式 R。** 正式开跑需用户裁决后另行执行。

## 8. 局限性与结论失效条件

1. **原假设是超总体意义上的 0**：AA 下每个用户的 `Y(标签=1) = Y(标签=0)`，标签独立于结果机制；
   有限总体下两组的样本均值差并不等于 0，那正是置信区间要覆盖的抽样波动。因此本文报告的是
   t/z 检验的**经验第一类错误率**，不是有限总体精确随机化检验的 p 值。
2. **结论只在"同条件 + 虚拟标签"这一构造下成立**。若把 AA 换成"购买零增量但照常发券"，
   利润真值为负，拒绝率是功效而不是错误率（§4、§5.4）。
3. **源码绑定**：`build_observed_pipeline` 会在每个 rep 前后哈希 `src/causal_growth/**/v3*.py`、
   `sql/v3*.sql` 与 `configs/v3*/**.yaml`。任一处变更都必须重跑 AA，不能沿用本文数字；
   本文 manifest 记录了本次源码快照哈希（`out/v3_phase_d_aa/<run>/aa_manifest.json`）。
4. **小样本零膨胀**：利润是零膨胀、右偏的连续量，Welch t 在每组数千人时通常足够准确；
   若把 n 降到数百人/组，t 检验的名义水平会偏离 α，此时 FPR 的偏离不能直接归因于链路错误。
5. **并发写盘的环境限制**：本轮有多个代理并行写 `v3*.py`，源码门禁按设计拒绝了不少 attempt
   （见 §5.6）。重试只针对两类环境故障，且同一 rep 序号重跑逐位相同，不改变结果；
   但它会拉长墙钟，并让单 rep 的"墙钟/CPU"比值不再是 1。
6. **`n=10,000` 的 FPR 不足以判定"FPR 精确等于 0.05"**；本文只声明"与 0.05 相符、
   未发现足以让 GOAL 验收带失效的结构性膨胀"，且把 MC 精度一并给出。
